# release

Proposed `name`: `release`.

Use it when a person asks to cut a git-flow release on a product repository: confirm the semver, bump the version files that project names, refresh the lock the way that project names, and finish with notes the person has approved.

## What it locks

The sequence is company-wide. The paths, the lock command, the tag prefix, the branch names, the finish hook, and where the notes are read are project facts. They live in that repository's `.agents/project.md` Release slot. The playbook does not copy itself into the product repository.

The tag and the release merge land on the production branch (`main` or `master`, as the slot records). A tag that exists only on the integration branch is not a release. Finish pushes with git-flow's notes-file and push flags. It does not force-push, skip hooks, or deploy. A hotfix is out of scope.

The semver and the notes are each confirmed with a structured question before the matching step runs. A proposed semver equal to or lower than the current top-level version aborts. Empty drafted notes abort. JSON versions are read and written with `jq` on the top-level `version` key. Composer refreshes the lock with `composer update --lock --no-scripts` (or the slot's command that does the same). A container run uses the Compose service name from the Release slot, not a container id. Finish stays `git flow release finish -f <notes> -p`.

## Suggested location

`skills/release/SKILL.md`. Not a stack pack: the sequence is git-flow, and every product repository already uses that workflow.

## Why it should not be auto-merged

Finishing a release pushes the production branch and creates a tag. A person reviews the playbook before product repositories can run it. Merging `skills/release/SKILL.md` is a maintainer action ([propose-never-promote](../../principles/propose-never-promote.md)).
