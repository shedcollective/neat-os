# wireframes

Produce the information architecture (IA) and wireframes for a site or product. Follow [conventions/design-ux-agents.md](../../conventions/design-ux-agents.md#wireframe-projects).

This is **not** a launch playbook. Locate neat-os the same way `init` does. **Do not** search the public web for neat-os. **Do not** copy this playbook into `.agents/skills/`.

## When to use

- The asker wants a primary navigation, sitemap, page layouts, canonical and SEO rules, and a clickable wireframe for a new or rebuilt site.
- The asker wants an existing wireframe updated from client feedback or a client layout board.

## When not to use

- Visual design, brand or Figma mockups (that is the design agent: [`mockup`](../mockup/SKILL.md)).
- Reviewing a live site (that is [`ux-audit`](../ux-audit/SKILL.md)).
- Building the production site, or opening a pull request in a product or client codebase. When separation matters, co-create through the code agent instead.

## Steps

1. **Intake.** Fill the card: client lead, lock owner, audience, deadline, the dedicated throwaway wireframe repository, the cloud agent model the asker wants, house style rules, confidential yes or no. Stop if the lock owner or the throwaway repository is missing.
2. **Gather every source in full.** Structure documents, the client's service or product material, meeting transcripts, email threads, whiteboard exports with their images, and any earlier IA. Pass the full text to the cloud agent, not a summary. A summary loses the detail the reviewer will look for first. Ask the asker for anything you cannot open. Do not brief around a missing source.
3. **Write the brief.** Goal, deliverables, hard constraints, conflict rules (which source wins for structure, for labels, for weight), success tests, and the sources. Read the brief back before you send it. Never send a placeholder or an empty follow-up.
4. **Deliverables in the throwaway repository**:
   - `docs/00-sources.md`: one lettered entry per source, what it is, what was used, and a precedence table. Each new round of feedback is a new lettered source.
   - `docs/01-primary-navigation.md`, `docs/02-sitemap.md` (every URL, page type, weight, purpose), `docs/03-page-layouts.md` (templates as ordered components), `docs/04-canonicals-and-seo.md`, `docs/05-content-matrix.md`.
   - `docs/06-decisions-log.md`: numbered decisions (`D-<n>`), each with options, the choice, the source it rests on, and a fallback. Open items in one list.
   - `mocks/`: a clickable greyscale HTML wireframe, one page per sitemap URL, generated by one build script. No hand-edited output. No external fonts, scripts or images.
   - `mocks/catalogue/`: the component library. Every block on every page is a named component with one interaction type.
5. **Keep it simple from the first pass.** The reviewer must find the main offer in the menu in about two seconds. Count the links and words in each open menu and report the counts. Labels only in menus; the explanation goes on the pages. The mock carries no banners, toggles, legends or notes on the canvas. Annotation lives in a sidebar.
6. **Name the units before you draw the pages.** Use a small set of interaction types with one shape each, for example: band, button, text link, card, tag, filter, static. Buttons do actions, links go places, filters are not tags, a static box is not a card. Give each card type its own look. Generate the sidebar component list from the page markup so it cannot disagree with the canvas.
7. **Search-friendly labels.** For each label, ask what a prospect would type to find it. Keep the client's term when it matches. Keep a coined term with a plain line beneath it when the client wants it. Rename to the searched term when they conflict, keep the old term on the page, and redirect the old slug. Drop acronyms and internal shorthand. Cite any keyword volume with its tool, region and date. Never invent a volume. A rename is a client decision: list it as open until the client lead confirms.
8. **Content stays visible.** No accordions or tabs that hide content from crawlers. Sections are real headings. Filters change what is shown, never what is in the HTML.
9. **Cover mobile and access in the first pass.** A mobile menu, keyboard use, focus order, and real buttons for actions. Check them in a headless browser at desktop and phone widths.
10. **Volatile names in one place.** A name the client has not settled is one constant in the builder, with a redirect from the old slug. A build guard fails if the retired name leaks into output.
11. **Checks in the build.** Every internal link and anchor resolves. Every page names only components in the library. Banned words fail the build. The house style rules hold (for example no em dashes). Re-running the build gives no diff.
12. **Open a pull request in the throwaway repository.** Use the branch preview for review. Report the pull request link, the preview link, the counts from step 5, what changed per page, the judgement calls, and the open items. In that dedicated throwaway repository, self-merge is allowed. Do not merge in this repository or in any product or client codebase. Never a product repository.
13. **Feedback rounds.** Each round: add the feedback as a new lettered source, apply only what it asks, log the decisions, and hold anything the client floated but did not decide as an open item. A client sketch is a layout, not a cut list: keep sections it does not draw unless told to cut them. Locked IA decisions win over a new sketch; log the clash.
14. **Independent review, once.** When the asker wants a fresh eye, run one or two reviewers with the same rubric (menu clarity, unit identity, link versus button, states, mobile, source coverage), then write one synthesis. Do not fan out many reviewers on the same question.
15. **Client-facing report.** When asked, write it present tense, from the top: no change history, no decision numbers, an evidence note per section. Hand it to the asker as a new draft document. The client lead sends it.

## Stop

Complete when the pull request and preview exist in the throwaway repository, every check in step 11 passes, and the asker has the links, counts and open items. Not complete if a source was summarised instead of supplied, a product or client codebase was touched, anything went to a client, or a client fact, figure or quote was invented.
